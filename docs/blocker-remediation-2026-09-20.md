## AKS-55 local browser authority

The baseline probe created a project (HTTP 201) from an untrusted browser origin without credentials in local-appliance mode. The result and original probe are retained in the task evidence bundle.

The launcher now defaults to local-appliance/required auth and supplies a fresh random token through the existing frontend environment interface. Tokens are neither persisted nor logged. The local frontend server supplies the selected runtime mode at the existing config URL so the checked-in demo default cannot override it; this public script contains no credentials. Configured tokens and OIDC remain supported; disabled auth requires explicit development/demo mode. The gateway independently rejects disabled/tokenless fallback in release/local-appliance, validates expected origins, and emits the requesting allowed origin rather than a comma-separated CORS header. Non-browser clients retain authenticated access without an Origin header.

The realtime upgrade was an alternate entry point bypassing REST authorization. It now validates origin and authentication before upgrading; each RPC applies the existing permission/resource policy using the original request. The shared realtime SDK gains an optional `authToken` parameter. Browser clients carry the credential in a base64url upgrade subprotocol; only `juliaflow` is negotiated back, and credentials are stripped before the HTTP library retains/logs the handshake. Native bearer headers and OIDC validation remain supported. No token is placed in a URL. The existing application needs no source changes. Dashboard subscriptions enforce their dashboard resource policy. Connection cleanup removes only the closed socket's subscriptions.

Local verification completed on Windows with Julia 1.12.6: 1,069 API gateway assertions, 37 boundary checks, 73 realtime checks, 46 audit/OIDC checks, 5 cleanup checks, 26 contract checks and 27 frontend checks pass. The local bootstrap smoke and the real local-frontend config/CORS check pass. The final live-browser smoke passes all three scenarios (33.1 seconds), including native browser upgrade credentials and the existing strict-mode workflow. The harness rejects server lifecycle errors or leaked raw/encoded credentials; both checks pass. Control-document sync against `87aa8166`, BRD traceability (46 historical items), and `git diff --check` pass. Earlier failed probes are retained: a cleanup callback bug, a closed-page health request, and browser local-network blocking of an intercepted test document were resolved without weakening the log gate. Full Windows/Debian release certification is not claimed. Tests cover rejected credentials/origins without state mutation, permitted browser and CLI operations, owner-only local backup export, viewer realtime restrictions, token setup and explicit development compatibility. Independent source-boundary investigation and the single candidate review completed. Both confirmed findings were addressed: dashboard policy binding and authenticated SDK transport. Real-browser execution also exposed and repaired a pre-existing subscription-cleanup callback bug. Shared test helpers were moved unchanged into unconditional setup after isolated auth/realtime slices exposed a hidden fixture dependency; no assertions or thresholds were removed. The original wildcard-health assertion was replaced with the intended no-Origin/no-CORS-header assertion, alongside positive origin-specific response tests.

No dependency or storage-schema migration is included. Rollback is a scoped revert, but reintroduces the recorded security defect and must not be treated as safe release configuration. Other AKS-41 acceptance and AKS-53/54/56 remain open. Review/merge and complete Windows/Debian release proof are separate gates.
