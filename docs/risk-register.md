# JuliaFlow Risk Register

Last updated: 2026-06-03

This register tracks active BRD delivery risks that should be burned down through thin, verified slices. It complements `docs/TODO.md`, `docs/brd-traceability.md`, `docs/project-tracker.md`, and `docs/checkpoint-log.md`.

## Current Risk Focus

Next implementation lane: local-first GA proof after the BRD v0.4.0 strategy refresh. The active risk burn-down now prioritizes local appliance bootstrap, local filesystem/DuckDB data estate, local PostgreSQL lab/team metadata mode, local CPU/GPU hardware validation, explainability/model evidence, offline Hub, academic reproducibility, and backup/restore. Provider-specific deployment, cloud object stores, external registries, enterprise identity, and cloud multi-GPU closure are optional compatibility paths rather than core GA blockers.

## Risk Burn-Down Order

1. Local appliance bootstrap: burn down `R-LOCAL-001`.
2. Local data estate: `R-DATA-001` is mitigated for the current managed-estate slice and replaces cloud object-store proof as the core storage gate.
3. Local metadata/database modes: `R-DB-001` is mitigated for the current metadata/database slice; backup/restore and migration integrity remain in the later backup/restore lane.
4. Local hardware runtime: `R-HW-001` is mitigated for the current hardware runtime slice; keep hardware-backed CUDA and multi-GPU evidence conditional on available local hardware.
5. Explainability/model evidence: burn down `R-XAI-001`.
6. Offline Hub: burn down `R-OFFLINE-001` and keep external registry proof optional.
7. Academic reproducibility: burn down `R-REPRO-001`.
8. Frontend/module depth and runtime policy: continue `R-FE-001` and `R-RUNTIME-001` only when they serve the local-first workflow.
9. Control-doc drift guard: keep `R-DOC-001` mitigated by running `npm run validate:control-doc-sync` before completion claims.
